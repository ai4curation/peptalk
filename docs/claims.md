# Claims files

A claims file lists specific claims about specific proteins, for `peptalk ask`. Each claim becomes one
question to the model: does this protein have this function, this domain, this catalytic residue, this
location? The answer is a verdict (`yes`, `no` or `uncertain`) and a short reason. The model reads the claim
and the sequence, nothing else, and is not asked to annotate the protein from scratch.

This is for checking annotations one at a time, for example a GO annotation, a UniProt active site, or a claim
from a curation review. It is also for building benchmarks: add the verdict you expect to each claim, and
`peptalk ask` reports how many verdicts agree.

```bash
peptalk ask examples/proteins.fasta --claims examples/claims.yaml -w confidence
```

## The YAML format

Write claims files by hand in YAML. Group the claims by protein, under the protein's id (the first word of
its FASTA header):

```yaml
proteins:
  Q2PAY3_wt:                          # the id in the FASTA file
    - task: ask-catalytic-residue     # which ask template
      params: {position: 436, residue: D}
      expected: yes                   # optional: the verdict you expect
      note: catalytic Asp of the HRD motif   # optional: kept with the result
    - task: ask-function
      params: {term: "GO:0004674", label: protein serine/threonine kinase activity}
      expected: yes
  A0ABQ0J1P6:
    - task: ask-domain
      params: {accession: PF00069, name: Pkinase}
      expected: no
      note: "decoy: a kinase domain on an ABC ATPase"
```

[`examples/claims.yaml`](../examples/claims.yaml) is a complete example. It has ten claims about the three
proteins in [`examples/proteins.fasta`](../examples/proteins.fasta), covering each ask template. Among them
are true claims, decoys, a stale claim (a residue the mutant no longer has), and a NOT-style claim that a
curator would reject.

A flat list works too, with the id on each claim:

```yaml
claims:
  - {id: Q2PAY3_wt, task: ask-localization, params: {compartment: rhoptry}, expected: yes}
```

| Field | Required | Meaning |
|---|---|---|
| protein id (key under `proteins`), or `id` | yes | the first word of the protein's FASTA header |
| `task` | yes | an ask template (below) |
| `params` | yes | that template's parameters, all of them, and no others |
| `expected` | no | `yes`, `no` or `uncertain`: the verdict you expect. It is never sent to the model and is not part of the cache key |
| `note` | no | any text. It is kept with the result and never sent |

Quote values that YAML would otherwise read as something else: GO ids (`"GO:0004674"`), and any text with a
colon followed by a space. An unquoted `yes` or `no` after `expected:` is read as intended.

Every claim is checked before any question is asked. An unknown task, a misspelt parameter or a missing one
stops the run with the place of the problem:

```
Error in claims file:
claims.yaml: proteins → Q2PAY3_wt → 1: ask-catalytic-residue takes no postion (it takes position, residue); missing position
```

## Ask templates and their parameters

<!-- params-table: generated by `peptalk tasks --ask`; tests/test_claims.py checks it is current -->
| Template | Parameters (claims-file columns) | Question |
|---|---|---|
| `ask-catalytic-residue` | `position`: 1-based residue position<br>`residue`: one-letter code expected at that position | Is residue R at position P catalytic? Verdict yes/no/uncertain |
| `ask-domain` | `accession`: Pfam accession, e.g. PF00069<br>`name`: Pfam short name, e.g. Pkinase | Does the protein contain this Pfam domain, and where? Verdict yes/no/uncertain |
| `ask-function` | `term`: GO term id, e.g. GO:0004672<br>`label`: GO term label, e.g. protein kinase activity | Does the protein have the function of a GO term? Verdict yes/no/uncertain |
| `ask-localization` | `compartment`: a cellular compartment, e.g. mitochondrial inner membrane | Is the protein located in compartment C? Verdict yes/no/uncertain |
<!-- /params-table -->

The prompts are printed by `peptalk tasks --show ask-domain`, and the answer schemas by
`peptalk tasks --schema ask-domain`. Two templates also check the claim itself against the sequence:

- **`ask-catalytic-residue`:** checks that the claimed residue is really at the claimed position
  (`claim_residue_matches_sequence`), and that the model read that position correctly.
- **`ask-domain`:** checks that the accession is a well-formed Pfam accession, and that any domain boundaries
  the model gives lie inside the sequence.

## TSV and CSV, for bulk input

For claims generated by a script, a table is simpler: one row per claim. The columns are `id`, `task`, one
column per parameter, and `expected` and `note`. Empty cells are left out, so one table can mix templates.
Lines starting with `#` are comments. The format follows the file extension: `.yaml`/`.yml`, `.tsv`/`.tab` or
`.csv`. [`examples/claims.tsv`](../examples/claims.tsv) holds the same claims as the YAML example.

## Output

Each claim gives one record, like any other answer. It carries the parsed `answer` (`verdict`, `reason`, and
any payload such as `confidence`), the claim's `params`, `expected` and `note`, and the checks. With
`--shuffle-control` each claim is also asked of a shuffled copy of the sequence, and a "yes" there flags the
real answer. The summary table (`-f tsv`) shows the verdict in `call` and your `expected` next to it. Here is
Claude Haiku 5.5 at low effort on `examples/claims.yaml` (some columns left out):

```
id                 task                   confidence     call         expected  flags
Q2PAY3_wt          ask-catalytic-residue  checks_passed  yes (0.85)   yes
Q2PAY3_wt          ask-catalytic-residue  checks_passed  no (0.85)    no
Q2PAY3_wt          ask-function           checks_passed  yes (0.80)   yes
Q2PAY3_wt          ask-localization       checks_passed  yes (0.60)   yes
Q2PAY3_asp_to_asn  ask-catalytic-residue  flagged        no (0.80)    no        claim_residue_matches_sequence: D436 is N436
Q2PAY3_asp_to_asn  ask-function           checks_passed  yes (0.82)   no
A0ABQ0J1P6         ask-domain             checks_passed  yes (0.92)   yes
A0ABQ0J1P6         ask-domain             checks_passed  no (0.95)    no
A0ABQ0J1P6         ask-function           checks_passed  yes (0.90)   yes
A0ABQ0J1P6         ask-localization       checks_passed  no (0.80)    no
10 answers (10 new calls, 0 reused, 0 errors, 1 flagged); 6196 input + 6486 output tokens; spent $0.0039; 9 of 10 verdicts match expected
```

The numbers in brackets are the model's stated confidence (`-w confidence`). The one disagreement is the
NOT-style claim: Haiku still gave the Asp436Asn mutant kinase activity. The stale catalytic-residue claim on
the mutant is flagged before anyone reads its verdict.

The claim's parameters, the header context and the payload are part of the cache key, so asking the same
claim again reuses the stored answer. `expected` and `note` are not, so correcting them never triggers new
calls.
