seqfun-annotator · design note · 25 November 2026

How should seqfun talk to model APIs?

seqfun-annotator sends one tool-free question per sequence and task to a frontier model, then parses, checks and prices the answer. This note compares four ways to build the provider layer, says what caching and batch APIs buy for this workload, and asks whether protein-function-agent should reuse it.

Decision, 25 November 2026

Direct clients for every provider. If calling close to the metal is best for Anthropic, it is best for all. seqfun keeps its own thin clients for Anthropic (Messages API), Gemini (generateContent) and OpenAI (Responses API). Each sends exactly the protocol, records the same provenance and passes the same input-token check. All three have batch support through their providers' batch APIs. Agents write and maintain this code, so the convenience of a wrapper does not decide it. llm is not used as the provider layer; llm templates for one-off reads are optional and low priority.

Logging and caching. Every call is logged with full provenance in a local SQLite store, which is also the cache. The cache key is a set of fields, by default the sequence MD5 (as UniParc uses), task, prompt version, provider, model and effort, so a renamed sequence still hits and a changed prompt never does.

Built to merge. Records are keyed by sequence checksum and call id, exports from different people merge without duplicates, and the annotated sequences can be written as FASTA for a DIAMOND or BLAST database. A shared, searchable database is designed (docs/shared-database.md), not built.

PFA. The host runs seqfun for the blind read and hands the JSON to the reviewer. PFA's merged prompt is now seqfun's combined task, marked untested.

Recommendation given before the decision

Every read goes as a direct, single-shot API call: the prompt and the sequence, and nothing else. That clean route is a core reason seqfun exists. fs2f's main Claude runs went through the Claude Code command line, which cannot rule out extra context or connector tools. Those runs should be treated as possibly contaminated, and seqfun is the tooling for repeating and extending them.

For Anthropic models, call the Messages API through the anthropic client ourselves (A). For every other provider, use llm as an optional extra (B). A gives exact control of every field in the request and shares one request builder with the half-price batch path. It also has fewer moving parts: one HTTP client, no plugins, no per-user llm settings. B gives uniform access to Gemini, OpenAI and any other plugin model without client code of ours. Ship the four prompts as llm templates as well, for one-off reads. Drop the hand-written Gemini and OpenAI clients. Don't use litellm.

For PFA: run the sequence read through seqfun on the host and hand the JSON to the reviewer, instead of running a tool-free managed-agent session for it.

Why direct API calls

fs2f asked its Claude questions through the Claude Code command line (claude -p --system-prompt "" --tools ""). That route adds context of its own and, on an account with connectors, can attach connector tools. fs2f's own check (experiments/decoy_control/README.md) measured the extra input:

The larger CLI figure most likely came from connector tools. Whether the stored fs2f rows carried such an attachment is not known: they record cost, not tokens. The revised flags still leave about 570 tokens the tool adds itself. A direct call to the Messages API, or to Gemini's generateContent or OpenAI's Responses API, carries only what the caller sends, and the reported input count can be checked against a token count of the prompt. seqfun is built on that route so that the fs2f results can be repeated cleanly, more robustly and at scale. Results from the CLI route should be read as possibly contaminated until they are.

Single-shot API calls: a refresher

Agent frameworks hide most of this. For a one-question, one-answer call, the practice that matters is:

  • Send exactly the protocol. One user message, no system prompt, no tools. Anything a client, wrapper or CLI adds becomes part of the experiment, so check the reported input tokens against a token count of the prompt.
  • Set effort explicitly. Defaults differ by model: Opus 5.5 defaults to medium, most others to high. Thinking is always on for Fable 5.2 and Opus 5.5, and adaptive thinking replaces fixed thinking budgets.
  • Leave room for thinking. Thinking counts toward max_tokens. fs2f saw Opus 4.6 hit 64,000 output tokens on structure questions. Stream long requests, or the HTTP call can time out.
  • Read stop_reason before the content. refusal (safety classifier, HTTP 200) and max_tokens both leave no usable answer.
  • Record provenance. Keep the served model (fallbacks can change it), the prompt hash, the effort, token counts including thinking, and cost.
  • Let the SDK retry 429s, 5xx and connection errors. Catch the SDK's own error classes only at the edge of the run, so one failure does not stop a batch of thousands.
  • Treat answers as samples. Temperature can't be set on these models, so a cache is the reproducibility record, not just a saving.

The four options

A · current code

Own thin clients

About 60 lines per provider over each provider's HTTP client package. For Anthropic that is anthropic: a typed client for the Messages API, not the Agent SDK, with nothing agentic in it. We set every field: the prompt, max_tokens, adaptive thinking and output_config.effort. The same request builder feeds the batch path.

full control we maintain each provider

B · llm as library

llm's Python API

llm.get_model(id).prompt(text, **options) for any model a plugin provides. llm-anthropic is itself built on the anthropic package and sends nearly the same request as A (captured below). llm-gemini sets thinking_level.

any plugin model options and errors differ by provider

C · templates + package

llm templates, thin package on llm

Templates carry prompt, model and options, so llm -t seqfun-feat -m claude-fable-5-2 -o thinking_effort high works for one sequence. The package does the rest on top of B.

zero-code one-offs template alone sends the FASTA header

D · excluded

litellm

Excluded at Chris's request after its past security and supply-chain incidents. It is also a large dependency for a tool that needs one request shape. A compatibility layer also tends to lag new provider parameters such as effort, adaptive thinking and refusal fallbacks.

not considered further

What templates alone cannot do
  • A template's $input is all of standard input. The FASTA header goes to the model, and a header like sp|P00533|EGFR_HUMAN gives the answer away. fs2f sent >sequence.
  • A multi-sequence FASTA becomes a single prompt.
  • Effort option names differ (thinking_effort for Claude, thinking_level for Gemini), so a template either fixes one provider or the user passes -o.
  • --schema switches to constrained decoding. fs2f asked for JSON in plain text, so schema variants are a new, untested route and should be opt-in.
  • No shuffled controls, residue checks, skipping of repeats, prices or batch.

Is llm awkward as a Python library?

Tested live with llm 0.38, llm-anthropic 0.31 and llm-gemini 0.38.1. For a single call it is not awkward:

B: llm

import llm

model = llm.get_model("anthropic/claude-fable-5-2")  # llm's id
r = model.prompt(prompt, thinking_effort="high")
# Gemini would need thinking_level="high"
text = r.text()
r.usage()   # Usage(input=36, output=15, details=
            #  {'output_tokens_details': {'thinking_tokens': 0}})
r.json()["model"], r.json()["stop_reason"]

A: Anthropic SDK

import anthropic

client = anthropic.Anthropic()
with client.messages.stream(
    model="claude-fable-5-2", max_tokens=64_000,
    messages=[{"role": "user", "content": prompt}],
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
) as s:
    msg = s.get_final_message()

What worked: model lookup, options as keyword arguments (validated, so a misspelt option is an error), Pydantic schemas, async models (llm.get_async_model), token usage with thinking, the raw response JSON, and keys from ANTHROPIC_API_KEY or llm keys. The Python API does not log to SQLite unless you call response.log_to_db().

So Chris's recollection is half right. Wrapping one call is easy. A tool that promises the same protocol on every provider still has to handle option names, errors and batch itself, which leaves llm with the transport and model discovery for providers seqfun does not otherwise support.

Caching

Result cache (ours)

A JSON file per completion, keyed by provider, model, effort and the full prompt. A rerun asks only what is missing, so an interrupted job of 5,000 proteins resumes where it stopped. Batch results are written to the same cache.

llm's log

The CLI logs every prompt and response to SQLite. It is a record, not a cache. llm does not skip a prompt it has already answered, and the Python API logs only when asked.

Provider prompt caching

Anthropic caches a marked prefix (cache_control). A read costs 0.1× input on most models, 0.05× on Opus 5.5 and 0.025× on Fable 5.2, and a write 1.25×. OpenAI caches prefixes of 1,024 tokens or more automatically. Gemini has implicit caching and explicit context caches with a storage fee.

For seqfun, provider caching does nothing. The fixed part of each prompt is 212 to 315 tokens, below Anthropic's 512-token minimum, and the sequence is the part that changes. Even if it cached, input is about 3.5% of the cost; thinking and output are the rest. A long shared system prompt, such as a Pfam list, would make caching pay, but it would also change the protocol being tested.

Batch APIs

A batch API takes many requests at once and returns the results later, at half price. All three providers have one:

What it buys

  • Half the cost. At fs2f's recorded median of $0.07 per Fable 5.2 features question, 10,000 proteins with shuffled controls come to about $700 by batch instead of $1,400.
  • No rate-limit handling or client-side concurrency.
  • High throughput, well suited to proteome-scale runs.

What it costs

  • Latency: minutes to a day, so not for interactive use.
  • An asynchronous workflow: a manifest, polling, then collecting. seqfun saves the manifest to disk, so a collect can run later from another shell.
  • No streaming and no server-side refusal fallback inside a batch.

Should protein-function-agent use seqfun?

PFA (PR #1) runs its sequence reader as a separate managed-agent session with no tools. The host writes the reader's only message, so the read is blind. Its prompt merges the keys of the FEAT, PSEUDO and STRFN questions into one, and that merged prompt was not itself tested in fs2f. Its validate.py repeats the residue-position and domain-bound checks that seqfun has. In the YrfG example the reader cost $0.12 and took 19 seconds.

Option 1: PFA imports seqfun's prompt, schema and checks

One source of prompts, answer models and checks. The reader stays a managed-agent session. Little change to PFA.

Option 2: the host runs seqfun, the reviewer gets the JSON recommended

A tool-free single question does not need an agent session or a sandbox. A direct call is just as blind, since the host still writes the message. It is also cached and recorded with the served model and cost. Many proteins can go by batch at half price, and the same reads serve curation pipelines outside PFA.

With option 2, add PFA's merged prompt to seqfun as a task (say combined), marked as an untested merge, so there is a single source of prompts. That also lets someone compare it with the three separate fs2f prompts on the fs2f test sets.
